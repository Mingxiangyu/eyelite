# 预告横幅「不出现 / 看起来卡住」——定性与证据

> 结论先说：**这不是"卡顿"，是"预告窗被整段跨过去"**。
> 用户描述"倒数到 2、1 卡住两三秒"，实际观测到的是**横幅根本没出现（或提前消失）→ 几秒后遮罩突然弹出**。
>
> 记录日期：2026-11-16　｜　被测产物：`2e33fb6` / `EyeLite.exe 478208 / md5 703f63f1…`
> 复现脚本：`tools/p3-preview-onset-check.py`　｜　trace 解析：`tools/trace-interval-check.py`

## 0. 先看这里：一个已被数据否掉的假设

**"倒计时刷新被 UI 线程顶住（重绘 / 键盘钩子 / 渐暗层）"——不成立。**

判据：`EYE_LITE_TRACE_UI` 写的 `P <ms> <sec>` 行，相邻两条的 `ms` 差就是 UI 线程两次刷新的真实间隔。
正常 ≈1000ms；若被顶住应出现 2000/3000ms。

累计 **97 个 P 间隔，最大 1029ms，≥2000ms 的 0 个**：

| 场景 | 间隔数 | 最大 | ≥2000ms |
|---|---|---|---|
| 干净条件（无演示窗） | 28 | 1026ms | 0 |
| 例程窗开（矢量动作） | 8 | 1018ms | 0 |
| 例程窗开（素材动作） | 35 | 1029ms | 0 |
| 持续键盘输入（125 次回调） | 7 | 1022ms | 0 |
| Preview=10 × dim=45 | 8 | 1029ms | 0 |
| Preview=10 × dim=0 | 8 | 1025ms | 0 |
| Preview=3 不打字（出现横幅的几次） | 3 | 1009ms | 0 |

顺带被否掉的还有：
- **"横幅刚出现时有一次性的 DWM/位图开销"**：`Preview=10` 的第一条 P 行（`9→8`，正是横幅刚出现那一刻）是 **1029 / 1016ms**。
- **"`PreviewSeconds=3` 时 2、1 特别慢"**：`3→2` 实测 1011~1027ms，`2→1` 实测 1011~1015ms。

> 以后再有人报"倒计时卡顿"，**先看本节**，不要再从"刷新被顶住"方向查。

## 1. 现象与剂量-反应数据

**判据（两条独立）**
- 横幅出现 = 该 PID 名下可见窗口，`200 < w ≤ 900` 且 `h ≤ 300`
- P 行 = `EYE_LITE_TRACE_UI` 的 `P <ms> <sec>`；无 P 行 ⇒ 预告**从未启动**（不是"启动了但没刷新"）

**公共配置**：`WorkMinutes=1`、`RestSeconds=10`、`IdleMinutes=0`、`DimAlphaMax=45`（除注明）、`MeetingGuardEnabled=0`、`SuppressOnFullscreen=0`

| 组 | 条件 | 样本 | 横幅出现 | 结果 |
|---|---|---|---|---|
| **A** | `Preview=3`，**不打字** | 6 次（另早期 5 次） | 4/6（早期 3/5） | **缺失 2/6 = 33%**（早期 2/5 = 40%；合计 4/11 ≈ 36%） |
| **B** | `Preview=3`，**55~63s 每 60ms 注入 F24**（跨过到点，触发 C3/C4 让路） | 8 次 | **0/8** | **缺失 8/8 = 100%** |
| C | `Preview=3`，**50~56s 注入**（到点前 4s 停手，不触发让路） | 6 次 | 4/6 | 与 A 同量级（33%） |
| D | `Preview=10`，dim=45 / dim=0 | 各 1 次 | 2/2 | 横幅正常，9 条 P |

**A 与 B 的唯一变量是"注入窗口是否覆盖到点"**：33% → 100%，是清晰的**剂量-反应**。

**遮罩时刻（B 组）**：6 次 63.4~63.6s（比配置 60s 晚 **~3.5s**，与让路一次 5s 的量级相符）、1 次 72.5s（多次让路累积）。
> B 组另有 2 次遮罩被记成 1.5/1.7s —— 那是**探针误报**，见第 3 节，数据已丢弃。

## 2. 两个原因（叠加，不是二选一）

### 原因一：3 秒的预告窗 + 1 秒的主 tick = 结构性错过
预告窗的进入条件是"剩余时间落在 `(0, PreviewSeconds]`"。`PreviewSeconds=3` 意味着这个窗口只存在 3 秒，
而驱动它的主 tick 是 1 秒一次 —— **只要有一拍踩偏（tick 迟到 / 首次对齐偏晚），整段窗口就被跨过去**，
于是"横幅一次都不出现"，然后遮罩按时弹出。这解释了 A 组的基线 33%。

### 原因二：`deferred`（临门一脚让路）把预告窗挡在门外
```csharp
// src/Program.cs:6849
if (!paused && !idle && !deferred && cfg.PreviewSeconds > 0)
```
只要 C3/C4 判定"用户正在输入/前台在白名单"，`deferred` 为真，**预告窗连启动的机会都没有**；
同时 `due` 被往后推，`left` 变大，那 3 秒的窗口更不可能落进来。
A(33%) → B(100%) 的差异就是它造成的。

### 一条源码线索（未验证，供修复参考）
```csharp
if (previewDueMs <= 0) previewDueMs = Clock.NowMs() + left;   // 只算一次，之后不复位
```
`due` 被让路推后之后，`leftAbs = previewDueMs - now` 会变成负数 → 预告再也不会启动。
**这能同时解释 33% 的基线跳过和 100% 的让路跳过**，建议修复时一并处理。

## 3. 修复方向与"修后验证"设计（尚未落地）

**修复方向（待实现）**
1. 预告窗的进入/退出都挂到 **200ms 快照**（与"到点反应"同一条思路），不再依赖 1 秒 tick 的相位；
2. 进入时记 `previewStartMs`，之后**至少显示 `max(PreviewSeconds, 3~5)` 秒**，不再用"剩余秒数落在窗口内"判定退出；
3. `due` 每次变动（让路/推迟/跳过）都**重置** `previewDueMs`；
4. 让路期间横幅**保留并给出说明文案**（如「正在输入，稍后提醒」），而不是被 `!deferred` 直接挡掉。

**修后验证（A/B 两组，各 6 次，每次 75 秒）**

| 组 | 条件 | 修前 | 修后应满足 |
|---|---|---|---|
| A | `Preview=3` 不打字 | 33% 无横幅 | **6/6 出现**，P 行 ≥2，间隔 ~1000ms |
| B | `Preview=3` + 55~63s 持续注入 | 100% 无横幅 | **6/6 出现且"最后可见 ≈ 遮罩时刻"**（全程不消失），P≥2，**文案含「正在输入，稍后提醒」**；停止注入后立刻进休息 |

复现命令：
```bash
python -u tools/p3-preview-onset-check.py repeat_quiet 6   --exe EyeLite-dev.exe   # A 组
python -u tools/p3-preview-onset-check.py repeat       6   --exe EyeLite-dev.exe   # B 组
```

## 4. 三个仪器坑（都会伪装成产品缺陷，务必先排除）

### 4.1 遮罩探针会把"无关窗口"认成遮罩（已修）
早期判据是"大尺寸 + 非 `WS_EX_TRANSPARENT` + 子窗口 ≥1"，在本机 **启动 1.5~1.7s 会误报**（出现过一个不可能的时刻）。
→ 改成 **"必须有一个子控件文本含『休息』"**（`RestForm` 恒有标题「休息一下」）。
尺寸会随 DPI/多屏变，而「休息」二字只有 RestForm 有。

### 4.2 本机"从屏幕取样"不可靠（已修）
`GetDC(NULL)+BitBlt` 在本会话抓到过**过期的桌面内容**（白底文字），据此判"画面没动"会得出完全错误的结论。
→ 一律用 `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT=2)` 让窗口自绘。
详见 `tools/shoot.py` 头部与 `tools/p3-motion-check.py` 头部「仪器坑」第 2 条。

### 4.3 验证"修复是否生效"不能只看"横幅出现了"（方法论）
半修复版（只改了"到点保留横幅"、没改"允许打字时进预告"）跑 B 组，横幅仍然 6/6 不出现——
看起来像"没修"，其实只是**另一处没改**。
→ 所以修后验证要**同时**看三样：横幅是否出现、**横幅存活区间是否覆盖到遮罩时刻**、**文案是否出现新分支的说明**。
文案是最硬的证据：它只能由新分支写出。
