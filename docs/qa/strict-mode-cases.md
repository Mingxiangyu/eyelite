**实测数据（v1.2.0 最终产物，md5 `b88f1585…`，共 6 次）**

```
60.52  64.52  60.53      ← 第 1 批（其中 64.52 为唯一异常）
60.52  60.57  60.63      ← 第 2 批
休息时长：8.94 / 8.95 / 7.95 / … 全部落在 8±2s
```

> **1 次 64.5s 的异常没有定位，如实记在这里**：
> 异常值恒为 **+4.0s**（不是连续漂移），且同批次其余轮次精确到 60.5s，
> 说明锚点时钟本身是对的，是某个环节停顿了 4 秒。
> 已排查并排除：遮罩窗体创建（已预热）、A2 的 `Opacity` 写入（降到 1s 一档后仍出现）、
> GDI 增长（空闲稳态零增长）。
> 最可能是本机负载导致的调度/合成停顿（测试时同时开着 WorkBuddy、Chrome 多标签、Python 测试进程）。
> **未验证的假设不写成结论**：这条记为"偶发 +4s，根因未定"，不作为已知缺陷，也不声称已修好。
| P0-D-1 | 离开超过 `IdleMinutes` → 计时暂停 | 剩余时间不再减少 | 脚本（`EYE_LITE_FAKE_IDLE_MS`） | ✅ 实测 PASS（对照 58.7s 弹 / 实验 95s 不弹） |
| P0-D-2 | 离开超过整个休息时长 → 周期直接重置（不弹遮罩） | 回来后**不立刻**弹 | 脚本（`EYE_LITE_FAKE_IDLE_FILE`） | ✅ 实测 PASS（写回 0 后 **59.7s** 才弹 = 走完整周期） |
| P0-D-3 | 休眠后回来，活跃时长**不包含**睡眠时段 | 剩余时间不会跳到 0 | 源码审查 | 🟡 **设计已审查，真休眠未实测** |

**实测方式**：`tools/p0a-timing-check.py`（只读观测，不注入按键不抢焦点）、`tools/p0d-idle-check.py`。
P0-A-1 / P0-A-2 实测 3 轮全 PASS：遮罩 60.76 / 60.70 / 60.72 s，休息 7.77 / 7.86 / 7.76 s。

> **D-2 为什么必须用"文件钩子"而不是环境变量**：这条用例要验证"回来之后"的行为，
> 必须在**同一个进程**里先让空闲很大（触发重置）、再把空闲清零（模拟人回来）。
> 而 Win32 不允许修改其他进程的环境变量，所以只能用运行期可重读的
> `EYE_LITE_FAKE_IDLE_FILE`。
>
> **归因判据**：写回 0 后 ≤10s 就弹 → 只是"暂停"（剩余时间还在）→ FAIL；
> ≥40s 才弹（约一个整周期）→ 周期确实被重置 → PASS。实测 59.7s。

> **为什么这个数字有说服力**：活跃累计 52s 后剩余约 8s。
> 若只是"暂停"，人回来后会在 **约 8 秒**内弹；实测 **59.7 秒 ≈ 一整个周期**。
> 两者相差 7 倍以上，不是容差边缘的巧合 —— 说明累加器真的被清零了。
> （`b88f1585` 上实测 59.7s，此前 `a7cb251e` 上 59.9s，两次一致。）
> 只验"不弹"是不够的 —— 暂停和重置在外部现象上都是"不弹"。

> **D-3 未实测的原因**：真休眠需要机器真的睡过去再唤醒，会打断用户且无法保证
> 其余用例环境干净。**没有为了凑 PASS 去改系统时钟或伪造 `DateTime.UtcNow`。**
> 源码审查结论：`sleptAway = (wallDelta - qpcDeltaSec > 60) || (qpcDeltaSec > 60)` 覆盖
> "QPC 真休眠停走"与"进程被挂起"两种硬件行为；休眠时段靠 `dt = 0` 不计入活跃时长，
> 方向是**单向丢时间、绝不多算**（系统时钟前跳也只会被当成休眠丢掉一段）。
> 另发现 `idleGapSeconds` 是只写不读的死字段，真正生效的只有 `dt = 0`。

| P0-B-1 | 预告横幅在到点前 `PreviewSeconds` 秒出现 | 50 ± 4 s（工作 60 s / 预告 30 s → 约 30 s 处） | 脚本 | ✅ PASS |
| P0-B-2 | 预告期**键盘零干预** | 钩子链观测不到吞键 | 脚本 | ✅ PASS |
| P0-B-3 | 预告期**不抢焦点** | 前台窗口句柄不变 | 脚本 | ✅ PASS |
| P0-B-4 | 到点后预告转全屏遮罩 | 横幅消失、遮罩出现 | 脚本 | ✅ PASS |
| P0-B-5 | 遮罩持续时长准确 | 8 ± 2 s | 脚本 | ✅ PASS |
| P0-B-6 | 「延后」= 阈值后移，本轮不结束 | 下次遮罩 = `PostponeMinutes*60 + PreviewSeconds` | 脚本 | ✅ PASS（330.9s） |
| P0-B-7 | 「跳过」= 满周期重新计时 | 下次遮罩 ≈ 整周期、下次预告 ≈ `PreviewSeconds` | 脚本 | ✅ PASS（60.9s / 30.8s） |
| P0-B-8 | 「立即休息」= 立刻进入遮罩 | 遮罩 ≤3s 出现 | 脚本 | ✅ PASS（0.13s） |

**实测方式**：`tools/p0b-preview-check.py`（B-1~B-5）、`tools/p0b-exits-check.py`（B-6~B-8）。
B-1~B-5 实测 2 轮全 PASS：T1 50.54 s / T2 观测到 1 次钩子事件 / T3 前台未变 / T4 10.33 s 转遮罩 / 遮罩 8.78 s。
B-6~B-8 在 v1.2.0 构建上实测 3/3 PASS（见上表秒数）。

> **B-6 的期望值算式（踩过一次坑）**：「延后」加的是**阈值**
> （`workLimitMs += PostponeMinutes`），不是"从现在起再等 N 分钟"。
> 点击发生在预告刚开始时，累计已经吃掉 `PreviewSeconds` 秒，
> 所以点击后到遮罩 = `PostponeMinutes*60 + PreviewSeconds` = 300 + 30 = **330s**。
> 按 300s 断言会得到**假 FAIL**。三次独立运行均为 330.9s，模型稳定。

> **三出口的点击方式**：预告横幅的按钮是真实 Win32 子窗口
> （`RoundButton : Button`），用 `EnumChildWindows` 按**文本前缀**匹配后
> `PostMessage` `WM_LBUTTONDOWN/UP` 即可，**不抢前台、不移动鼠标**。
> 注意「延后」的真实窗口文本是「**延后 5 分**」（随 `PostponeMinutes` 变），
> 按"延后"精确匹配会永远找不到按钮。

> **仪器可信度前置条件**：任何靠钩子链观测的用例，必须先跑 `tools/p0b-hook-selfcheck.py` 确认仪器本身能收到事件。
> 仪器故障会伪装成产品缺陷（ctypes 回调签名写错时回调异常被静默吞掉，表现为"钩子装上了但永远收不到事件"）。

## P0-C · 系统通知状态闸门（FullscreenDndGate）

判定方式：脚本 `tools/p0c-gate-check.py`，用环境变量 `EYE_LITE_FORCE_QUNS` 强制状态覆盖真实 API。

| ID | 用例 | QUNS | 期望 | 状态 |
|---|---|---|---|---|
| P0-C-1 | 运行时全屏 D3D → **不弹**遮罩、**不弹**预告 | 4 | 无遮罩、无横幅 | ✅ 实测 PASS |
| P0-C-2 | 使用 D3D 全屏 → 同上 | 2 | 同上 | ✅ 实测 PASS |
| P0-C-3 | 演示模式 → 同上 | 3 | 同上 | ✅ 实测 PASS |
| P0-C-4 | **系统免打扰 → 照常弹**（本机真实状态） | 5 | 有横幅 + 有遮罩 | ✅ 实测 PASS |
| P0-C-5 | 正常状态 → 照常弹 | 0 | 有横幅 + 有遮罩 | ✅ 实测 PASS |
| P0-C-6 | 关闭 `SuppressOnFullscreen` + QUNS=4 → 照常弹 | 4 | 有横幅 + 有遮罩 | ✅ 实测 PASS |
| P0-C-7 | 抑制期**不装键盘钩子**、不吞按键 | 4 | 钩子链观测不到吞键 | ✅ 实测 PASS（F24 2/2/2 放行、Ctrl 成对） |
| P0-C-8 | 抑制解除后立刻补弹，不重复计时 | 4 → 0 | 改状态→遮罩 ≤5s | ✅ 实测 PASS（**0.52s**） |
| P0-C-9 | 抑制超过上限强制放行 | 4 | 遮罩出现 | ✅ 实测 PASS（**62.7s**；修复前**永不弹**） |

> **P0-C-9 曾是真 bug（v1.2.0 修复）**：旧实现到上限时把 `isSuppressed` 置 false 后 `return`，
> 下一个 tick `blocked` 仍为真 → `if (!isSuppressed)` 又成立 → **重新开始计 30 分钟**。
> 结果只每 30 分钟弹一条托盘气泡，**遮罩永远不出现**，与契约 §10.1.1 第 ③ 条直接矛盾。
> 修法：新增 `suppressForced` 标记，到上限时**保持 `isSuppressed` 为 true、不 return**，
> 落到正常到点判定；标记只在"抑制真正解除"或 `BeginRest` 时复位。

> **P0-C-8 / C-9 的驱动方式**：`EYE_LITE_FORCE_QUNS` 是静态只读、且 Win32 不允许修改其他进程的
> 环境变量，所以运行中无法把 QUNS 从 4 改成 0。为此新增 `EYE_LITE_FORCE_QUNS_FILE`（每次
> `Query()` 重读文件内容，0~6 优先于 `EYE_LITE_FORCE_QUNS`），C-9 另用
> `EYE_LITE_SUPPRESS_MAX_MS` 把 30 分钟上限压到 60 秒，免挂机。
> **这两个环境变量仅供自动化测试，生产环境不要设置**（不设则零影响）。

**实测结果**（`tools/p0c-gate-check.py`，2026-11-14，三轮迭代后 6/6 PASS）

```
T1 QUNS=4 RUNNING_D3D_FULL_SCREEN   PASS  preview=no overlay=no  (expect overlay=False)
T2 QUNS=2 USING_D3D_FULL_SCREEN     PASS  preview=no overlay=no  (expect overlay=False)
T3 QUNS=3 PRESENTATION_MODE         PASS  preview=no overlay=no  (expect overlay=False)
T4 QUNS=5 QUIET_TIME (本机真实状态)  PASS  preview=28.9s overlay=58.7s (expect overlay=True)
T5 QUNS=0 NOTIFICATION_FORCED_ON    PASS  preview=29.7s overlay=59.5s (expect overlay=True)
T6 QUNS=4 + 关闭开关                 PASS  preview=28.6s overlay=58.5s (expect overlay=True)

=== P0-C summary: 6/6 PASS ===
```

注意 T4/T5/T6 的 `preview` 与 `overlay` **都必须有**：抑制用例要求两者**都没有**
（横幅也要被压住），放行用例要求两者**都有**（走完整 P0-B 预告流程）。
早先版本只断言 overlay，漏掉了横幅，已修。

**仪器踩坑记录（两处，都是"仪器缺陷伪装成产品缺陷"）**

1. `overlay_windows()` 用 `w > 800 and h > 500` 判定，把 **Windows 桌面窗口
   （Program Manager，3840×2160）** 当成了 EyeLite 遮罩 → 全部用例误报
   `overlay@0.0s`。修法：`GetWindowThreadProcessId` 取 PID，只认 EyeLite 自己的窗口。
2. `eyelite_pid()` 每次轮询都调 `tasklist`（0.3~1 秒），在 0.15 秒的轮询间隔里
   把观测节奏拖垮，导致"遮罩明明在，脚本却说没有"（T4 误报 FAIL）。
   修法：PID 缓存（`Popen` 直接拿 `proc.pid`）+ 轮询降到 0.05 秒。

**抑制源白名单（实测确定，契约 v11 §10.1.1）**

| QUNS | 含义 | 抑制 |
|---|---|---|
| 0 | `NOTIFICATION_FORCED_ON` | ❌ |
| 1 | `BUSY` | ✅ |
| 2 | `USING_D3D_FULL_SCREEN` | ✅ |
| 3 | `PRESENTATION_MODE` | ✅ |
| 4 | `RUNNING_D3D_FULL_SCREEN` | ✅ |
| 5 | `QUIET_TIME` | ❌ **实测修正** |
| 6 | `BUSY_DND` | ❌ **实测修正** |

> **为什么 5 / 6 不抑制**：本机 `QUNS` 恒为 5（Win11 系统级免打扰常开，无 `FocusAssist` 注册表项）。
> 照调研文档 C1 原文把它当硬抑制源，本机 EyeLite 会**永不提醒**。详见契约 v11 §10.1.1。

|---|---|---|---|---|
| P0-E-1 | 默认配置（`StrictMode=0`）下，休息期间普通按键**照常输入** | 能正常打字 | 脚本 `T1` | ✅ 实测 PASS（2026-11-14） |
| P0-E-2 | 默认配置下，Esc / 空格仍能跳过 | 休息结束 | 脚本 | ✅ 实测 PASS（T4 覆盖） |
| P0-E-3 | `StrictMode=1` 时键盘被锁 | 无法打字，Esc / 空格可退出 | 脚本 `T3` 对照组 | ✅ 实测 PASS（吞键已证实可见） |
| P0-E-4 | **Ctrl 不卡住**：休息期间 Ctrl 成对通过或成对吞掉，绝不半吞 | down/up 必须成对 | 脚本 `T2` / `T3b` | ✅ 实测 PASS（2026-11-14） |
| P0-E-5 | 休息结束后物理键全部释放 | 七键全 `up` | 脚本 `T2b` / `T4` | ✅ 实测 PASS（2026-11-14） |

**实测结果**（`tools/p0e-input-check.py`，2026-11-14）

```
observer hook installed (WH_KEYBOARD_LL), 前置于 EyeLite 的钩子
instrument selfcheck: PASS（F24 down/up 均被 observer 看到，2 条）
orig config: StrictMode=0 WorkMinutes=20 RestSeconds=20

T3  严格档对照组（仪器应看得见吞键）  PASS  遮罩61.3s F24 被放行=0 条(期望0)
T3b 严格档裸 Ctrl 配对               PASS  down=0 up=0 共0条
T1  默认档遮罩期按键送达（输入未被吞）  PASS  遮罩61.5s F24 放行=2 条（期望 2）
T2  默认档裸 Ctrl 必须送达且成对      PASS  down=1 up=1 共2条
T2b 默认档连续按键后物理键无残留        PASS  stuck=无
T4  休息结束后物理键全部释放           PASS  stuck=无

=== P0-E summary: 5/5 PASS（不含对照组）===
```

**判定方法（v2，钩子链）**：低级键盘钩子按「最后安装的最先调用」执行，
任一钩子返回非 0 则链终止。脚本在**启动 EyeLite 之前**装好 observer，
于是 EyeLite 休息期装的钩子排在它之后（先被调用）——observer 收到 = 放行，
收不到 = 被吞。全程不建窗口、不抢前台、只注入不产生字符的 `VK_F24` 与裸 `Ctrl`。

> **为什么必须有 T3 对照组**：没有它，"默认档没吞键"可能只是仪器瞎了。
> 先证明仪器在严格档下确实"看不见"按键，再证明默认档下"看得见"，结论才成立。

> **P0-E-4 的成对性判据**：只放行 down 不放行 up（或反之）会让应用侧认为
> Ctrl 一直按着 —— 这正是用户报告过的「ctrl 一直卡住」的根因形态。
> 因此合法结果只有两种：**2 条且 down/up 各 1**，或 **0 条全吞**。半吞一律 FAIL。

**仪器踩坑记录（三次，同源）**：都是"仪器缺陷伪装成产品缺陷"。

1. `SetWindowsHookExW` 的 `hinst` 传 32 位残句柄 → `err=126 ERROR_MOD_NOT_FOUND`。
   根因：`GetModuleHandleW` 未声明 `restype`，64 位句柄被截断。
2. `keybd_event(VK_CONTROL)` 实际产出的 `vkCode` 是 **`VK_LCONTROL(0xA2)`**，
   不是 `VK_CONTROL(0x11)`。只比 `0x11` 会把消息全漏掉，表现为
   "默认档也放行 0 条"这种**假 PASS**。修法：`CTRL_VKS = (0x11, 0xA2)`。
3. v1 用 `SetForegroundWindow` 抢前台做判定 —— 既抢不到（前台锁），
   又**与"不得影响用户输入"这条待验证目标自相矛盾**。改用钩子链后彻底不需要前台。

## P0-A2 · 休息前渐进降饱和（v1.2.0 新增）

| ID | 用例 | 期望 | 判定 | 状态 |
|---|---|---|---|---|
| P0-A2-1 | 剩余 ≤60s 时压暗层出现 | 出现，且**不是**休息遮罩 | 脚本 | ✅ 实测 PASS（60.6s） |
| P0-A2-2 | 到点时遮罩仍然出现（压暗层不吞掉提醒） | 遮罩在压暗之后出现 | 脚本 | ✅ 实测 PASS（压暗后 60.0s） |
| P0-A2-3 | 有任何键鼠输入 → 撤销且**本轮不再尝试** | 4s 内消失、之后不再出现 | 脚本 | ✅ 实测 PASS（0.87s） |
| P0-A2-4 | `DimAlphaMax=0` 时一个窗口都不建 | 全程无压暗层、无遮罩 | 脚本 | ✅ 实测 PASS |

**判定方法**：`tools/p0a2-a3-check.py`。
压暗层与遮罩的区分是本节的关键——**不能只看尺寸**：

```
dim     = w>800 and h>500 and (WS_EX_TRANSPARENT) and 子窗口数 == 0
overlay = w>800 and h>500 and !(WS_EX_TRANSPARENT) and 子窗口数 >= 1
```

> **为什么需要这条判据**：`DimForm` 铺满整块屏幕，尺寸与遮罩完全相同。
> 只用 `w>800 and h>500` 会把压暗层当成遮罩，导致**所有**按尺寸判定的脚本
> 报"遮罩立刻出现"（实测把 C-8/C-9 骗成两条假 FAIL）。
> 这是本机第 3 次"仪器缺陷伪装成产品缺陷"。

|---|---|---|---|
| **抑制上限不生效** | 全屏/演示挂满 30 分钟，只弹一条托盘气泡，**遮罩永不出现** | 到上限把 `isSuppressed` 置 false 后 `return`，下一 tick 又 `if (!isSuppressed)` 重新计时 | 新增 `suppressForced`：到上限**保持 `isSuppressed=true` 且不 return**，落到正常到点判定 |

> 我第一版把"懒创建的一次性分配"判成"GDI 泄漏"，还写进了文档；

## 通用纪律

1. **观测优先于注入**：能用只读观测（窗口枚举 / 计时 / 进程内存）判定的，不要注入按键。
2. **仪器先自检**：任何依赖钩子链的判定，先跑仪器自检脚本。
3. **窗口识别必须按 PID 过滤**：Windows 桌面（`Program Manager` / `WorkerW`）本身就是一个
   3840×2160 的可见顶层窗口，不按进程过滤会把它当成遮罩，表现为"遮罩立刻出现"，
   所有用例全错。这个坑已经踩过一次。
4. **配置必须还原**：任何改过 `%APPDATA%\EyeLite\config.ini` 的测试，结束后必须还原用户原值
   （含未识别的自定义键，不能只写已知键列表）。
5. **"大尺寸"不足以判遮罩**：A2 的压暗层铺满屏幕、尺寸与遮罩一致。
   必须再加两条：`WS_EX_TRANSPARENT`（压暗层有、遮罩没有）与**子窗口数**（遮罩有 Label/按钮，压暗层没有）。
6. **观察用的钩子本身会吞键**：`CallNextHookEx` 未声明 `argtypes` 时，`lparam` 被按 32 位转换，
   keyup 的 `0xC0000001` 溢出 → 回调抛异常 → ctypes 返回 0 → **观察钩子把用户的 keyup 吞掉**。
   "只观测"的仪器反而卡住输入，比判据错严重得多。所有 `SetWindowsHookEx` 类脚本都要过一遍 `argtypes`。
7. **所有返回句柄的 P/Invoke 必须显式声明签名**：`GetModuleHandleW` 漏 `restype` → 64 位句柄被截断 →
   `SetWindowsHookEx` 报 `err=126`；`GetWindowLongW` 漏声明 → HWND 按 32 位传。
8. **不要把"没测出来"写成"通过"**：本轮 C-8（QUNS 运行期不可改）与 D-3（需真休眠）
   都如实标为 SKIP / 未实测，并给出"为什么测不了"与"要测需要什么条件"。

## `settings` 项为什么只能 SKIP

本程序**没有**"二次启动打开设置页"的行为——第二次启动只弹一个 364×163 的提示框
「护眼小助手已经在运行了，请看任务栏右下角托盘」（标题同样叫"护眼小助手"，
我一度把它当成设置页，属于误判）。真正打开设置页只能点托盘图标，
而 Win11 托盘图标可能被折叠进溢出面板，用 `TB_` 消息点击既不稳定又会抢前台。

所以 `settings` 项只观察已打开的设置窗；要验这一项，请**手动打开设置页**后单独跑：

```bash
python tools/p1-batch23-check.py settings
```
